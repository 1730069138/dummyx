# 实际 VLA 推理部署调试记录

本文记录 DummyX 真实机械臂连接远程 OpenPI Pi0 推理服务器时遇到的主要问题、定位过程和最终方案。

## 1. 正确启动方式

客户端：

```bash
cd /home/jun/dummyx/webgui
python run.py deploy
```

远程推理服务器：

```bash
cd ~/VLA/openpi
CUDA_VISIBLE_DEVICES=4 XLA_PYTHON_CLIENT_MEM_FRACTION=0.9 \
uv run scripts/serve_policy.py policy:checkpoint \
  --policy.config=pi0_dummy_real_lora \
  --policy.dir=checkpoints/pi0_dummy_real_lora/dummy_real_lora_run001/40000
```

服务端使用 GPU 4；JAX 检查结果应为 `backend: gpu`，并能看到一个 `CudaDevice`。

## 2. RealSense 报 `No device connected`

现象：客户端启动时在 `pipeline.start(config)` 失败。

排查：

```bash
rs-enumerate-devices -s
```

实际连接的两台 D415 序列号为：

- 全局相机：`821312060126`
- 手腕相机：`816612062572`

处理：将部署脚本中的错误手腕相机序列号改为实际序列号，并将两路彩色流设为 `424×240 @ 30 FPS`。

## 3. 客户端刷新卡顿、重复打印等待日志

现象：相机读取、网络推理和电机控制互相阻塞；“算力严重不足，正在等待”等相同日志持续刷屏。

处理：

- 相机由独立线程持续洗帧，推理始终读取最新画面。
- Pi0 网络推理由独立线程负责，主线程只负责固定频率下发动作。
- 请求和结果各使用容量为 1 的队列，避免积压过时观测或动作。
- 相同等待/连接错误只打印一次，状态变化后才重新打印。

结果：客户端控制循环不再被单次网络推理直接卡住。

## 4. WebSocket `keepalive ping timeout`

现象：

```text
received 1011 (internal error) keepalive ping timeout
sent 1011 (internal error) keepalive ping timeout
```

服务端同时出现首次推理约 `26 s`、第二次约 `7.5 s`，后续稳定在约 `0.18–0.21 s`。

原因：首次请求触发 JAX/XLA 编译和模型预热，长时间同步推理可能使连接错过心跳；这不是机械臂控制频率本身不足。模型稳定后，单次生成动作块约需 `0.18–0.21 s`。

处理：

- 客户端使用可靠 WebSocket 连接参数：`ping_interval=20`、`ping_timeout=60`、`open_timeout=3`、`close_timeout=2`。
- 推理异常后丢弃失效连接并自动重建。
- 服务端启动后先完成一次预热，再开始真实机械臂实验。
- 服务端应避免让耗时推理阻塞 WebSocket 的 asyncio 事件循环；若仍发生心跳超时，应把同步 `policy.infer()` 放到工作线程执行。

服务端稳定推理时间已经远小于 60 秒时，仍频繁超时应继续检查 SSH/Tailscale 网络和服务端事件循环，而不是继续放大客户端动作间隔。

## 5. 动作块长度与执行速度

训练配置最初使用 `action_horizon=40`，测试过 80 步动作块。80 步时服务端一次推理约 `0.209 s`，但动作块更长不等于动作执行更快：

- 动作块越长，单次推理覆盖时间越久，网络开销相对更低。
- 动作块越长，后半段动作使用的是更旧观测，更容易出现来回犹豫或纠偏滞后。
- 修改训练配置中的 `action_horizon` 后，应使用一致配置训练和部署；不能只把输出长度当作控制频率旋钮。

最终客户端直接执行 Pi0 输出，不加入 ACT 时序融合等其他算法。

## 6. 每步限幅导致动作慢

现象：原部署脚本按控制频率计算每步最大角度，再裁剪 Pi0 输出，动作明显变慢。

结论：该限幅属于旧部署端安全策略，不是 Pi0 训练数据或模型结构的硬性要求。

处理：按实验要求删除每步增量限幅，直接使用 Pi0 的绝对关节目标；保留七个关节的绝对软限位和夹爪受阻保护。

注意：删除每步限幅会提高动作速度，也会提高真实机械臂的运动风险。运行时必须保留人工急停条件，并先在低风险空间验证。

## 7. 动作块之间停顿、衔接不连续

现象：执行完一整块才请求下一次推理，会产生约 `0.18–0.21 s` 的停顿；动作看起来一段一段。

处理：加入尾部预取。在当前动作块剩余少量动作时，用最新图像和关节状态并行请求下一块，当前块继续执行，推理结果准备好后直接衔接。

最终参数：

```python
EXECUTION_HZ = 50.0
PREFETCH_ACTIONS = 3
```

含义：客户端以最高 50 Hz 下发 Pi0 动作；当前块剩余 3 步时发起下一次推理。50 Hz 是目标上限，Python 调度、CAN 总线和系统负载仍可能使实际频率略低。

`PREFETCH_ACTIONS=3` 仅给推理留下约 `3 / 50 = 0.06 s`，小于当前约 `0.2 s` 的推理耗时，因此网络抖动时仍可能短暂停顿。若更重视连续性，可适当增大预取步数；代价是下一块观测会更早、更旧。

## 8. 9000 步仍未完成自动失败

问题：策略长时间运行仍未完成抓取时，实验缺少统一终止条件。

处理：增加：

```python
MAX_TOTAL_STEPS = 9000
```

执行完第 9000 个控制步仍未结束时：

1. 不再下发下一步动作；
2. 自动将本次实验判定为失败；
3. 执行现有平滑回待机位、关闭 CAN 和相机流程；
4. 跳过人工成功确认，但仍询问是否发生意外碰撞；
5. 将结果写入累计实验统计。

理想 50 Hz 下，9000 步约为 180 秒；实际总时间还包括首次推理、网络等待和重连。

## 9. 当前最终结构

```text
双 RealSense 相机线程
        ↓ 最新图像
Pi0 推理线程 ← 容量 1 的请求/结果队列
        ↓ 动作块
50 Hz 主控制循环 → 绝对软限位/夹爪保护 → CAN 电机
        ↓
尾部 3 步预取下一块；9000 步自动失败并安全收尾
```

当前关键配置位于 `webgui/apps/deploy_real_arm_vanilla.py`：

- `SERVER_IP`、`SERVER_PORT`：远程推理服务器地址；
- `SN_GLOBAL`、`SN_WRIST`：相机序列号；
- `EXECUTION_HZ = 50.0`：客户端目标控制频率；
- `PREFETCH_ACTIONS = 3`：动作块尾部预取点；
- `MAX_TOTAL_STEPS = 9000`：自动失败上限；
- `JOINT_LIMITS`：必须保留的绝对关节软限位。

## 10. 推荐调试顺序

1. 用 `rs-enumerate-devices -s` 确认两台相机序列号。
2. 用 JAX 命令确认推理服务确实运行在指定 GPU。
3. 启动服务端，确认 checkpoint 和 norm stats 加载完成。
4. 先发一次测试推理完成 JAX/XLA 预热；不能用首次推理耗时代表稳定性能。
5. 确认稳定推理约 `0.18–0.21 s`，且 WebSocket 不再心跳超时。
6. 检查待机姿态、软限位、急停和机械臂周围空间。
7. 启动客户端，观察动作块编号、块内步数、推理耗时和总步数。
8. 出现停顿时先比较“剩余动作覆盖时间”和“推理耗时”，再调整预取量；不要盲目增大动作块。
9. 达到 9000 步未完成时应自动失败并安全收尾。
